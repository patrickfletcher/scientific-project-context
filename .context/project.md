Read when: starting work, checking repository intent or current reality, or deciding whether another context source is needed.

Keep this file brief. `.context/index.md` points to focused context only when a task needs it.

`.context/scientific-practice.md` is the stable scientific contract. This file records how that contract applies to this product repository.

## Purpose and Useful Outcome

**What this project does**: Develops Scientific Project Context, a lightweight project-local system for maintaining the consequential facts, expectations, constraints, checks, and working context needed to understand, change, verify, and eventually explain scientific work.

**Who uses the result and what useful outcome they need**: Scientists working with coding agents, and their collaborators, need a project-owned record they can ask agents to consult and maintain, then review and edit themselves. The record should provide enough trustworthy context for the next meaningful step, without an onboarding questionnaire or a permanent documentation program. `.context/product.md` owns the detailed product promise.

## Current Reality

**Main materials and entry points**:

- `template/` contains the packaged Markdown: the eight-file starter set placed into a project, including the generated `.context/index.md` and four Agent Skills.
- `pyproject.toml` and `src/scientific_project_context/` define the experimental package, immutable resource catalog, bounded project operations, state-reporting check library, versioned reports, and `spctx` CLI.
- root `.context/` is this repository's own current product, planning, and evidence context; its reference layer is limited to one rationale and one evidence ledger.
- root `.agents/skills/` contains the same four self-contained Agent Skills shipped in the starter set.
- `tools/` contains the repository-only artifact verifier; `tests/` contains product contracts for the packaged Markdown resources and CLI.

**How work is performed, checked, and packaged**: `AGENTS.md` owns the environment and the exact command inventory. In summary, the repository installs locally with pip, ships the `spctx` CLI, and is verified by unit tests, a syntax check, a maintainer starter-resource contract, and a built-artifact membership check.

**Conditions and dependencies**: Runtime code uses only the Python standard library and declares Python 3.10 through 3.14. Hatchling is a build-only dependency. Source is `0.1.0.dev27`. The package is local and experimental, with no automatic upgrade or semantic migration.

## Scientific Work, Evidence, and Outputs

**What must not be changed silently**: Packaged resources in `template/`, accepted product meaning, and recorded trial observations. Generated project context and public text remain review-required until confirmed.

**What could make the result wrong even if the workflow completes or looks plausible**: The system could be mechanically consistent yet burden users, conceal project-specific scientific risk, prompt invented meaning, overwrite project knowledge, or encourage claims beyond retained evidence. Real use added five observed failure modes: context can land on the wrong surface and be duplicated across all three, this product's private vocabulary can leak into a scientific project, the CLI can be absent from the agent's `PATH` while the report text still presents it as the normal route, the always-read update rule plus the practice core's obligations can turn project context into a log of what was run, kept, and approved while the scientific answer gets hard to find, and evidence and staleness rules read without their level can become scripts that hash their own source and refuse to run when it changes. Product tests could also become ceremonial by checking retired internal mechanisms rather than shipped resources and commands.

**Smallest useful check**: New initialization must install the exact starter contract with the complete managed project-context route, the `Project Essentials` prompts including where `spctx` lives, and structurally valid, self-contained Agent Skills, and the report must ask for that block by name and print the interpreter it ran from. Retrofit preview/apply must retain every occupied regular starter file byte-for-byte, install only safe missing files, defer a missing `AGENTS.md` that would activate retained unreviewed practice or skill content, and expose the exact compact route without editing occupied instructions. `--claude` must add one pointer per skill carrying that project's own description, never overwrite an occupied pointer, and never copy a procedure body. Index dry-runs must expose exact planned bytes, list every Markdown file under `.context/` with its `Purpose` and `Read when` lines, and never discard text a project added to the index. `check` must report the scientific-practice core, Agent Skill structure, pointer agreement, index integrity, routing guidance, and review markers, and report route state and remaining starter prompts as state lines rather than findings, without reporting a path the project's `.gitignore` files exclude as missing; rerunning this root must report no observations. Shipped text must ask for current state rather than run history and must carry no promotion, authority, or ownership vocabulary.

**Current evidence and limits**: Product tests, syntax and root checks pass, and the package builds and verifies at dev27; `.context/evaluation.md` holds the tested platform range and the anonymized observations from use. Uncontrolled use in the author's own trial repository exposed defects now fixed in source; an explicitly prompted trial there tuned all three descriptions and preserved them across an upgrade. A colleague's three-week trial completed every setup step and kept the scientific habits the prompts asked for, but its context grew into a defensive run log that two cleanups did not fix. Whether dev23 and dev24 prevent that is untested. These observations are not agent-behavior trials. Published host documentation describes skill discovery, but no Claude Code session has followed a pointer skill, and no controlled Codex or Copilot Chat session has verified discovery, automatic selection, or adherence to the revised procedures. Unprompted tuning, the effect of tuned triggers, manual migrations, the declared Python floor, other platforms, and real-use namespace clarity remain untested. No hook behavior, security, latency, or compatibility observation exists.

Every statement this project makes about product effect is exploratory. Only the mechanical behavior of the code paths the tests exercise is settled enough for anything to rely on, and that establishes nothing about human ease, domain adequacy, scientific reproducibility, publication readiness, or release readiness.

**Important assumptions or settings**: Scientists and relevant domain reviewers decide scientific meaning; project, data, and community authorities decide permitted change, use, and sharing; people and agents decide when another document is useful; tools perform bounded mechanics. Files placed into a project become project-owned snapshots. The experimental package has no runtime dependencies, telemetry, automatic upgrade, or automatic semantic migration.

**What later work depends on**: the eight-file starter set and the four-command interface; the division of authority in the line above; the rule that no command rewrites a project-owned region; the rule that `.context/index.md` is generated and is the only list of context documents; and the rule that `check` reports state rather than passing or failing a project. Everything else, including the wording of any prompt, report line, or procedure step, can still change.

## Unresolved Questions

- Do controlled use or renewed registry checks expose a material reason to change the provisional `scientific-project-context`, `scientific_project_context`, or `spctx` identity before public upload?
- How should the repository be shared: a wheel, a zip of the current files, or a public repository whose history starts at a single snapshot? The private repository's history holds earlier, identifying versions of the trial records, so it should not become public as it is.
- Should the `init` report's remaining machine vocabulary move out of human output entirely? dev17 translated the visible labels, state names, step names, and finding text into plain language while leaving the JSON field values unchanged. What remains visible is `Result:` and `Mode:`, whose values are still machine tokens such as `ready_with_activation_deferred`. Translating those is possible but would either lose the exact state or need a second vocabulary to maintain.
- Should the public README show a worked example of a populated `.context/project.md`? Shelved on 2026-09-23, with three options recorded for when the public surface is filled out. A short synthetic example from a generic domain is the likely first step: it is brief, needs nobody's permission, and can be labeled illustrative. This repository's own `.context/` is already a real example and is linked from the README, though it is a software product rather than a bench or analysis project and so does not show the scientific fields at their most useful. Linking to adopters' live context documents would be the strongest evidence, but that only becomes possible after adoption and requires their agreement.
- Does real use show that contributors recover consequential state more accurately or efficiently without disproportionate reading or question burden?
- Should an inventory-loading failure diagnose stale editable-install metadata/source combinations and suggest reinstalling? The first root attempt reported dev4 while current source expected the dev6 five-file inventory; the version mismatch was visible, but the remediation was not.
- Should `init` report where `spctx` was installed from, beside the interpreter it already names? Installed metadata records the source, so recording the upgrade command would not need `pip freeze`. Held while report fields stay still for the trials.
- Do the four canonical `.agents/skills/` procedures trigger accurately in clean Codex-extension and Copilot Chat sessions without disproportionate maintenance burden? The self-announcement line added in dev17 is what should make this observable.
- Parked: should context documents become a valid Open Knowledge Format bundle? Its `description` frontmatter matches the `Purpose` line, but conforming would add YAML, including a `type` field, to every document; `.context/automation.md` explains why no frontmatter ships now.
- Parked: does one flat index stop scaling? If a project needs listings per folder, each would be a generated `index.md`, as `.context/product.md` states.
- Do `spctx-public-writing` and `spctx-literature` each earn a permanent place in the starter? Public writing was added for one recurring field failure; in later trials it was possibly used for author text in one and stalled unattended poster work in another, so dev26 lightened it. The literature skill was added in dev26 because three trial projects devised their own source-strength labels and citation-checking rules, and one project's own review found unchecked recollections steering its design rules. Neither has a controlled selection observation.
- Does an opt-in, read-only session-start `spctx check` hook expose otherwise-missed structural activation failures with low enough latency, noise, trust, and compatibility burden to justify packaging host-specific adapters? Retain the no-hook default and do not treat non-execution or a structural pass as semantic freshness. T2's failures were all in prose, which a hook would not have seen.
- Does gating evidence on what depends on a result change agent and user behavior, or become an excuse to skip warranted checks? The core has defined levels since 2026-09-25; every trial project still restated the exploratory default by hand, so dev26 puts it in the routing block, drops the named middle level, keeps the relied-on list light, and reserves the strict reproducibility standard for publication. Whether projects stop writing overrides, and whether the relied-on list gets used once ceremony is lower, are the open measures.
- Which of the remaining candidates, if any, earns its cost? A dated one-line decision log, a documented way to turn the system down or out such as a minimal starter, and a durable record of declined suggestions. The outcome measure and a review mode were adopted in dev26 on trial evidence; the rest still need a reason from a trial.

Current package mechanics live in `.context/automation.md`; the open decisions above still require user review.

## Sharing and Reuse

The repository currently exposes a local prototype. Experimental artifacts have been built and checked locally, but they are not published and must not be described as a supported release. The MIT license, added on 2026-09-23 and confirmed by the author on 2026-10-02, grants permission to use, modify, and redistribute the source; it does not make the interface stable or supported. Trial repositories, their owners, and their content must not be identifiable from this repository; `.context/evaluation.md` owns how observations are recorded. When a real paper companion, archive, package release, or external handoff occurs, confirmed facts may seed public documentation; authorship, claims, citation, availability, ethics, governance, support, and stewardship remain reviewed decisions.
